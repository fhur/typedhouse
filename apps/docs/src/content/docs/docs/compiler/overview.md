The **Simplifying Compiler** produces SQL that is easier for ClickHouse to plan. It addresses a familiar problem: manually tweaking SQL statements to help the database produce better query plans. Instead of making callers repeatedly move filters, trim unused columns, or remove unnecessary subqueries, this layer applies well-established, widely recognized query optimizations automatically wherever it can prove they are safe.

Its job is to simplify the SQL presented to ClickHouse—not to replace ClickHouse's optimizer. You compose queries around your application's logic; the simplifying compiler removes avoidable complexity while preserving their meaning. ClickHouse remains responsible for choosing the execution plan, and simpler SQL does not guarantee faster execution for every query.

`compile` from `@typedhouse/compiler` validates the original relational graph, performs logical rewrites, validates again, analyzes column demand, plans shared CTEs, plans SELECT blocks, and emits SQL. It does not mutate your original query graph.

Each optimization page includes a standalone TypeScript example followed by its **actual final SQL and parameters**. The SQL is generated by executing the example against the compiler, with whitespace formatting for readability. All passes run together: a filter-pushdown example may also benefit from pruning and SELECT-block folding.

## Choosing the compiler

The examples call `compile(query.ir)` directly and export the result. To use the same compiler through `query.toSQL()`, import `registerCompiler` from `@typedhouse/core` and register `compile`, as explained in [Getting started](/docs/getting-started/). `client.run` compiles independently of that registration.

## Safety boundaries

A **fence** is an operation a particular transformation cannot safely cross. For example, moving a filter before a limit would change which rows are selected. Raw SQL, volatile or potentially failing expressions, and unsupported shapes can also prevent transformations. Unsupported optimization shapes keep their boundaries rather than receiving speculative rewrites.

Logical rewrites repeat until no rule applies. A decreasing measure checks progress; a 50-pass safety limit fails rather than returning a partially converged rewrite.

Rewrites retain parameter object identity. Placeholder allocation follows the emitted SQL, so use the returned `sql` and `params` together rather than assuming fixed parameter numbering. See [parameters and compiler outputs](/docs/reference/parameters/).

## Current limits and validation

These transformations preserve query meaning, but do not promise faster execution for every query. ClickHouse still chooses the execution plan, and CTEs are not an execution cache.

SELECT-block folding supports direct CTE references, safe integer arithmetic projections over scans and filters, a `DISTINCT` flag before sorting and limiting, and one `ARRAY JOIN` per scan block. Selection merging and filter pushdown substitute only expressions inside the compiler's closed total fragment; an expression that could fail or change value keeps its original evaluation set.

Currently absent: outer-join rewrites, join reordering, cost/statistics-based planning, explicit PREWHERE movement, limit/top-k pushdown through UNION, and real temporary-table materialization.

The nested `emitNaive` backend remains a reference for differential tests. Compiler tests cover safety boundaries and SQL shapes; integration suites compare optimized and naive results on ClickHouse. These checks are not a universal performance proof or completion of every planned optimizer acceptance test.
